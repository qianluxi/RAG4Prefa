# 报告身份与干净重跑（2026-10-29）

专家复审 P0-2 点名的两件事：**①报告里的"代码身份"在脏工作区等于没记；②关键实验应当从
最新干净提交重跑。** 这份记录是第一件的做法与第二件的结果。

结论先放这里：

1. 补的是**源码内容哈希**（`src_sha`），不是 `git diff`。同 `src_sha` ⇒ 影响数字的源码
   逐字节相同，这个判断在脏工作区里也成立。
2. 9 份关键报告从干净提交重跑（`47b7297`，`src_sha 9cb5bf5ad67c`），**40 行指标里 38 行
   一字不差**——旧报告的数字是对的，缺的只是身份。
3. 变的 2 行落在同一份报告里、而且是**对调**（`rerank` 0.839→0.871、`rerank_parallel`
   0.871→0.839）。顺着这条线量出了重排服务的抖动：**同一份代码、间隔 3 分钟，1 题**，
   而同一批次里不调重排的 `hybrid` 行 **0 题变化**。
4. 由此推翻（或至少降级）此前两处说法，见 §5。其中一处是**我自己上一轮写给专家的判断**：
   "0.871 与 0.839 是 rrf 与 zscore 的正常差值，不是漂移"——对了一半，另一半是漂移，
   而且这两个效应**恰好落在同一对数字上**，单看数字分不开。

---

## 1. 问题：20 份报告的代码身份是空的

`_code_state()` 原来只记 `git rev-parse --short HEAD` 加一个 `dirty` 布尔。报告头因此长这样：

```
- 生成于 2026-10-29T14:26:00+08:00 · 代码 `3c77c36`（有未提交改动）
```

`eval/reports/` 下有 20 份是这种形态。它们的问题不是"没记录"，而是**记录了一条误导信息**：
跑出那组数字的代码并不是 `3c77c36`，而是 `3c77c36` 加上当时工作区里那些还没提交的改动
（zscore 融合本身就是这么跑出来的）。而报告恰恰最常在"改完还没提交"的时候生成——这是
评测脚本的日常状态，不是例外。

## 2. 补了什么：内容哈希，不是 diff

```python
_FINGERPRINT_ROOTS = ("rag4prefa", "scripts/eval.py")
_FINGERPRINT_SUFFIXES = frozenset({".py", ".json"})
```

做法：`git ls-files --cached --others --exclude-standard` 列出这些路径下的文件（**含已
`git add` 之前的未跟踪文件**，否则"新写了一个模块但还没提交"这段状态又看不见了），逐文件
算 sha256，把 `路径 + \0 + 内容哈希` 按路径排序灌进一个总 sha256，取前 12 位。

三个刻意的选择：

| 选择 | 理由 |
|---|---|
| 内容哈希，不用 `git diff` | diff 只说"跟某个提交比变过"，不说"变成什么"。两份报告都标着"有改动"时，diff 救不了你——它们的改动可能压根不是同一处 |
| 只覆盖 `.py` / `.json`，且只在 `rag4prefa/**` + `scripts/eval.py` | 改 README、加个一次性诊断脚本不该让上一份报告显得不可比。**指纹一旦对无关改动敏感，人就会开始无视它** |
| 词表的 `.json` 必须计入 | 报告名里只有词表的**文件名**（`-termmap-public_to_standard.v2`）。原地改几条映射，文件名一个字都不变 |

### 2.1 两个当场踩到的坑

**CRLF**：`.gitattributes` 写的是 `eol=lf`，但 Windows 上 `core.autocrlf=true`，工作区的
`scripts/eval.py` 1450 行全是 CRLF。哈希读磁盘字节，于是同一份代码在 Linux 检出后算出另一个
`src_sha`——"报告上那个 sha 可以被别人当场复算"这句话当场失效，而它正是加指纹的全部理由。
归一化 `\r\n → \n` 后再进哈希：指纹认内容，不认磁盘格式。

**文件名被吃掉一个字**：`git status --porcelain` 的首行是 ` M scripts/eval.py`（状态位前有
空格），原实现对整段输出 `.strip()`，把首行的前导空格也吃了，之后按固定列切路径得到
`cripts/eval.py`。这个 bug 一直在，只是以前没人用过这些文件名。

### 2.2 怎么复算

```bash
python scripts/eval.py --print-fingerprint
# {"commit": "47b7297", "dirty": false,
#  "src_sha": "9cb5bf5ad67c", "src_files": 39}
```

报告头现在长这样：

```
- 生成于 2026-10-29T17:50:51+08:00 · 代码 `47b7297` · 源码 sha `9cb5bf5ad67c`（39 个文件）（工作区干净）
```

脏的时候会把**文件名**也列出来（最多 4 个 + 总数）：指纹回答"变没变"，文件名回答"变在哪"。
前者能判等，后者能定位，两件事不能只做一件。

> `commit` 与 `src_sha` 有时会不同步（比如只改了 README 的那次提交）：`commit` 会往后跳，
> `src_sha` 不动。这不是 bug，**它是这两个字段分工的证明**——数字只受 `src_sha` 管。
> 写这份文档时正好又撞上一次：工作区脏着 `HANDOFF.md`、`README.md`，`dirty: true`，而
> `src_sha` 仍与九份报告一致（`9cb5bf5ad67c`）——也就是说，那 9 份报告与"现在的代码"
> 在影响检索的部分上**是同一份**，改两句文档没有让它们失去可比性。

## 3. 干净重跑：40 行里 38 行一字不差

口径：`47b7297`，工作区干净，`src_sha 9cb5bf5ad67c`，2026-10-29 17:40~18:10 一个批次跑完。
参数**逐份照原报告头部抄**（`--modes`、`--top-k`、`--term-form`、`--term-rerank`、`--fusion`
都从旧报告里读出来，不凭记忆），不是按今天的默认值重跑。

| 报告 | 变化的行 |
|---|---|
| 基础集 31 题 `fusionrrf` / `fusionzscore` | 无（5 行 × 2 份全同） |
| 基础集 + 词表 v2 `terms`（含 `-rerank`） | 无（4 行全同） |
| 基础集 + 词表 v2 `terms -rerankappend` | **`rerank` 0.839→0.871、`rerank_parallel` 0.871→0.839** |
| 口语集 50 题 `fusionrrf` / `fusionzscore` | 无（5 行 × 2 份全同） |
| 口语集 + 词表 v2 `terms` / `joined`（`-rerankappend`） | 无（4 行 × 2 份全同） |
| 口语集 + 词表 v1 `terms -rerankappend` | 无（2 行全同） |

合计 **38/40 行逐位相同**。也就是说：旧报告的数字本身是可信的，缺的只是"这份数字出自哪份
代码"。归档的 9 份原样留在 `eval/reports/archive/*.as-of-<提交>-dirty.*`，不删。

变的那 2 行在同一份报告里**对调**——这是关键线索：不是"词表变好了"，是**有 1 题在两行之间
换了位置**，而这两行只差"重排查询是不是术语串"。

## 4. 顺着这条线量出重排抖动：1 题 / 3 分钟

同一批次里有两次运行，**在 `rerank` 这一行上是完全相同的配置**（`rerank` 行不含术语通道，
重排读原话），前后相隔 3 分钟：

| 时间 | 报告 | `hybrid` | `rerank` |
|---|---|---|---|
| 17:50 | 基础集基线（zscore） | 0.871 | **0.871** |
| 17:53 | 基础集 + 词表 v2 `terms` | 0.871 | **0.839** |

`hybrid` 行 — **0 题变化**。`rerank` 行 — **1 题**，就是它：

```
施工图审查评分表中装配式内装设计 Q1 项的满分是多少？
   hybrid 第 1 名（四次运行都是 1）
   rerank 名次：17:47 → 无 / 17:50 → 4 / 17:53 → 无 / 17:56 → 5
```

融合后的池子里它**稳定在第 1**，是重排把它推到 4、5、或直接推出前 5。同一道题在 9 分钟内
四次运行出四种结果，而每一步的输入都一样。这不是"配置差异"，是远程重排服务自己的抖动。

**这条对照行是关键**：如果只是"整批数字都动了"，那可能是模型、语料、代码任一环节；
`hybrid` 一行不动、只有调远程服务的那一行动，才把责任锁死在重排侧。

一题 = 0.032（31 题分母）。所以本仓库那句"小于 2 题的差别不要单独解释"，现在有了直接测量，
不再只是经验。

## 5. 被推翻或降级的三句话

### 5.1 "0.871 与 0.839 是 rrf 与 zscore 的正常差值" — 对了一半

上一轮我给专家的判断是"这两个数不是漂移，是两组报告的正常差值"。干净重跑显示：

- rrf 的 `rerank` = **0.839**，zscore 的 `rerank` = **0.871**（同批次，17:47 vs 17:50）→ 真有差异，1 题；
- zscore 的 `rerank` 自己在 17:50 与 17:53 之间也在这两个值之间跳 → 也是 1 题。

**两个效应撞在同一对数字上。** 所以专家的怀疑是对的（不能归因），我那句"不是漂移"是错的
（确实是漂移，只是恰好也是融合差异）。更准确的表述是：**在 31 题的分母上，"融合方式的真实
差异"和"重排服务的抖动"都是 1 题，单看总数无法区分**，只能靠"同一批次里的对照行"去判。

### 5.2 "词表在专业问法集上 +0.032" — 符号不稳，本质是噪声

| 运行 | `rerank` | `rerank_parallel` | 差 |
|---|---|---|---|
| 旧（脏）append | 0.839 | 0.871 | **+0.032** |
| 干净 terms | 0.839 | 0.806 | −0.032 |
| 干净 append | 0.871 | 0.839 | **−0.032** |

同一份词表、同一个形态，两次干净运行给出相反符号。**"专业问法集不亏"应降级为"看不出影响"**，
而不是"略有益处"。这也说明：此前把"专业问法集不亏"当作 `append` 可以上生产的依据之一，
那个依据本身站不住——`append` 该不该上，只能靠口语集那 4 赢 0 输。

### 5.3 误触发的代价，第一次量到了（而且 `append` 确实挡住了它）

P0-1 判定 `pipeline-hidden` 在「架空楼地面内敷设管线时，检修口宜设置在什么位置？」上是误触发
（命中的是"检**修**"的"修"）。这一轮它有了检索代价：

| 形态 | 注入 | `hybrid` | `hybrid_parallel` | `rerank` | `rerank_parallel` |
|---|---|---|---|---|---|
| `terms` | 管线分离 / 维修更换 | 1 | 1 | 1 | **无** |
| `append` | 管线分离 / 维修更换 | 1 | 1 | 1 | **1** |

召回四行不动（原话通道没被碰，gold 本来就在第 1），差别只在重排查询：`terms` 把原话换成了
"术语串"，重排于是不再读"检修口"；`append` 保留原话，损伤为零。**同一处误触发，代价完全
取决于形态**——这是 `append` 设为推荐形态的第一个直接证据，比口语集那 14/15 更贴机制。

## 6. 没做的事

- **11 份脏报告没重跑**：`expand-parallel-*`、`termmap-terms-w0{3,5}`、`termmap-joined-w1-rerank`
  等，都是已被证伪的旧实验线（结论在 HANDOFF 第三十八~四十轮），重跑只烧额度不产出新结论。
  它们仍留在 `eval/reports/`，删不删是另一个决定。
- **重排抖动只能测，不能消。** 这一轮的产出是"它有多大"，不是"它怎么修"。真要压，得换成本地
  重排模型、或对同一候选池重排多次取并集——都是另一轮的工作。
- **语料侧仍未核**：专家提的"OCR 缺页 vs 检索没找到"要单独做，`eval/corpus-audit-20261028.md`
  那次是 `--ocr off` 跑的，这一轮没碰。
- **`rerank` 行的收益判据**：本轮的结论是"不能再拿 `rerank` 行的 Recall 差当融合收益"。至于
  该用什么替代（固定候选池重排多次？池深 25 的赢输题数？），需要下一轮定下来。
