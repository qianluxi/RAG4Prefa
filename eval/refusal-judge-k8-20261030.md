# 判官对照实验（生产深度 k=8）与评测缓存身份（2026-10-30）

> 上一轮（`eval/refusal-judge-siliconflow-20261030.md`）的结论是"v2 误拒 3.3%、库外 85%，
> 不接入阻断"。这一轮按专家复审的三条优先级做：**先修评测缓存身份**，再**完善地域与时间
> 适用性**，最后**把判官实验对齐生产 `top_k=8`**。
>
> 结论与上一轮一致的地方：三版都不接入阻断。**不一致的地方更重要：这一层本身不是确定性
> 测量——同一份输入连跑两次，155 题里 8~11 题结论翻转。** 于是"v2 比 v3 好多少"这种问题
> 在当前口径下没有答案，只有 v1 与 v2 之间二十几题的差距是可信的。

---

## 一、为什么把 k 从 5 提到 8

生产链路 `settings.top_k = 8`：送给大模型的是前 8 条片段。此前判官只看前 5 条，与生产
不一致——判官说"这批片段答不了"时，生产的模型其实还能看到第 6~8 条。

提到 8 不会动候选池：`_hybrid_pool_size(k) = max(k*5, 50)`，k=5 与 k=8 都是 50 深。
变的只有"重排后返回几条"和"判官读几条"，是受控变量。

历史两轮的数字都在 k=5，**不能与本轮的 k=8 直接比**——看到片段越少，判官越容易判不可。

## 二、三版在同一批冻结候选上的对照

同一批候选（`eval/reports/judge-hits-k8.json`，155 × 8 条，语料 75 份 / 2560 片段）、
同一个模型（`Qwen/Qwen3.5-35B-A3B` @ 硅基流动）、同一天：

| 判官 | 库外 33 题（该拒） | 库内 122 题（不该拒） | 判官未表态 |
|---|---:|---:|---:|
| 规则闸门 | 7 | 0 | — |
| v1（单一口径，温度 0.2） | **32** | 28（23.0%） | 0 |
| v2（按问法分型，温度 0.2，第一次） | 29 | 6（4.9%） | 0 |
| v2（同上，第二次） | 30 | 8（6.6%） | 0 |
| v3（同对象/同适用条件 + 输出前自检，温度 0.2） | 30 | 10（8.2%） | 1 |
| v2（温度 0，第一次） | 28 | **4（3.3%）** | 0 |
| v2（温度 0，第二次） | 29 | 5（4.1%） | 0 |

v1 的 28 题误拒按性质拆开（`scripts/diagnose_judge.py`，`--k 8`）：

| 分栏 | 题数 | 含义 |
|---|---:|---|
| gold 在它看到的 8 条里却判「不可」 | 20 | 判官读走了眼 |
| gold 不在 8 条里却判「不可」 | 8 | 它说的是真话，责任在检索 |

## 三、v3 没有变好，而且好不好的判断本身不成立

v3 改了两处（细节见 `prompts.SYSTEM_JUDGE_V3`）：

1. 取值型从"同类型取值"拆成**三条并列**：同类型 / 同对象 / 同适用条件，缺一条即不可；
2. 加**输出前自检**：理由里出现"未明确/未给出/缺少"却写「可」，把第一行改成「不可」。

第 2 条针对的是上一轮最刺眼的失效形态——判官在理由里明明写了"未明确具体数值"，第一行
却写「可」。按道理这条应该把漏掉的那 3 道取值型题补上。

实测（v2 第一次 → v3）：

- 库外多拦 1 题（`装配式装修的碳排放怎么核算？`、"装修完多久能住进去？" 被 v3 拦住，
  `装配式内装有没有对应的国际标准？` 从「不可」退化成格式不可解析）；
- 库内多误拒 4 题（老房子翻新能补多少钱 / 厨房没窗户还能装燃气表吗 / 装修完怎么判断
  能不能住进去 / 十五五期间绍兴在住房上要干哪几件事）。

**一进四出，而且这四个进出都在下一节量出来的抖动范围内。** 所以正确的话不是"v3 不如 v2"，
而是"v3 与 v2 的差别测不出来"。

## 四、这一层不是确定性测量：同一配置连跑两次，8~11 题翻转

同一套提示词、同一个模型，每组各跑两次。0.2 的两次共用一份候选，0.0 的两次共用另一份
（两份候选为什么不同，见本节末尾）：

| 温度 | 两次的库外拦截 | 两次的库内误拒 | 逐题翻转 |
|---|---|---|---:|
| 0.2（配置默认） | 29 / 30 | 6 / 8 | **11 / 155** |
| 0.0（`JUDGE_TEMPERATURE`） | 28 / 29 | 4 / 5 | **8 / 155** |

温度 0.2 两次运行之间翻转的 11 题里有 4 道库内题从「可」变「不可」、1 道从「不可」变
「可」，其余在库外题之间来回。定温到 0 把翻转从 11 降到 8，**但没有消除**——远端服务在
temperature=0 下也不是逐字节确定的（批处理、算子实现都可能导致）。

这条结论的用法很具体：

- **≤4 题的版本差异不可解释。** v2 与 v3 的差别（库外 1 题、库内 4 题）落在这个区间里；
- **v1 与 v2 的差别可信**：库内误拒 28 对 4~8，差二十几题，是抖动解释不了的；
- 以后要比较版本，**必须跑 3 次取多数票**，或者把结论写成"28~30 / 4~8"这样的区间。
  单跑一次的"这条提示词提升了 1 题"没有意义。

**表格两行用的不是同一批候选，这一点也得交代。** 0.0 那两次是 `--rebuild` 重新检索出来的
（候选存在 `judge-hits.json`，`src_sha` 随之变成 `014d5e31`）；三版对照用的是更早取的那份
（`judge-hits-k8.json`，`6c0bd19f`）。把两份候选逐题比：

| 比较项 | 155 题里 |
|---|---:|
| top-8 顺序变了 | 60 |
| top-8 **集合**变了（有候选进/出池） | **17** |

也就是说，同一批问题、同一套代码、同一个重排服务，重检索一遍就会有 17 题的候选池边界挪动。
那 60 题的顺序变化不影响判官（它按内容逐条判，不看名次），但 17 题的集合变化会。

于是"温度 0.2 → 0"这件事要拆开看：

- 跨池对比（0.2 池 A → 0.0 池 B）：翻转 10 题，其中只有 2 题落在"顺序变了"的题上、
  **0 题落在"集合变了"的 17 题上**——所以这次翻转主要不是池子换人造成的；
- 同池重跑（0.0 的 a/b 两次，候选完全冻结）：本身就是 **8 题**翻转。

两个数字同量级。所以能说的话只有：**定温没有变好，也没有变坏，它只是把抖动从 11 降到 8，
而 8 仍然比"版本之间 1~4 题的差别"大**。不能宣称"定温解决了不稳定"，也不能用 6~8 → 4~5 的
改善当作温度的功劳。

顺带一个独立结论：**检索的池边界本身就不稳定**。这解释了此前记的"单次运行 Recall@5 有 ±1 题
地板"，也意味着任何以"gold 有没有进池"为机制的结论（比如词表 2×2 里 11/14 → 14/14 的池内
覆盖率）都要按这个幅度打折——池内覆盖率是硬约束，但它是**会漂的**硬约束。

修的东西：`LLM.complete()` 加了 `temperature` 覆盖参数，判官链路固定传 0
（`scripts/judge_sufficiency.py` 的 `JUDGE_TEMPERATURE`）。温度也进了判官结论缓存的
身份——0.2 与 0 的结论不能互用，这一点和"换服务商"是同一类事实。

## 五、评测缓存身份（专家复审第三节，已修）

改动集中在 `scripts/cache_identity.py`（新增）与 `scripts/judge_sufficiency.py`。

| 缓存 | 现在的身份 | 以前 |
|---|---|---|
| 检索候选 | 问题 + **Filter**、召回方式、深度、**语料文档数/片段数/id 摘要**、**源码指纹** | 只按问题文本做 key，元数据写了但不校验 |
| 判官结论 | 版本、模型、**服务商地址**、**思考设置**、**温度**、k、**提示词指纹**、**候选 id 摘要** + 问题 | 版本、模型、k、问题 |

三条设计选择值得记：

1. **加载时校验，不符就抛错**，不是"当作没缓存重跑"。后者对实验安全、对成本不安全，
   而且会让人以为是命中率低。报错里逐字段列出差异，并指明 `--rebuild` / `--rejudge`。
2. **候选摘要在判官 key 里**。提示词没变、模型没变，但检索结果变了（语料更新、融合改动），
   同一句话的片段就不是同一批，旧结论不能当新结论用。
3. **判官缓存不放源码指纹**。它太粗：改一句注释会让几百次调用白花，而那对判官结论毫无
   影响。判官的依赖面用提示词指纹 + 候选摘要表达，比源码指纹精确。

这套校验在本轮真实拦下过一次：重跑时忘了传 `--cache`，默认路径上那份上一轮的旧缓存
（k=5、无身份）被当场拒绝，而不是被当成 8 条的候选继续用。

代价也要说清楚：`src_sha` 覆盖整个 `rag4prefa/`，本轮为了给 `complete()` 加温度参数改了
适配器，候选缓存就整份失效、155 题重检索了一遍——虽然那次改动对检索毫无影响。这属于
"宁可多花一次检索，也不要用错一次候选"的取舍，但确实是个已知的粗粒度。

## 六、地域与时间适用性（专家复审第四节）

**地域：城市问题允许上一级文件作答，直辖市不允许。**

问「杭州」而库里只有《浙江省…标准》时，原来会因为文件名里没有"杭州"而拒答——省级标准
适用于省内城市，这是误拒。现在按 `PROVINCE_OF` 逐级看：本市有文件 → 直接用；只有省级
文件 → **不拒**，但挂一条非阻断信号 `geo_upper_level`，让用户看到"这是省级口径，未必是
本市的具体规定"。

直辖市（北京/天津/上海/重庆）故意不挂到全国：库里有 GB 标准，不等于有北京的申报口径。
这条是护栏——挂上去，库外集里 7 道地域题会全部失效。

**时间：年份区间也走资料年语义。**

专家给的原句：「到2027年，2021—2023年间老旧小区改造任务进展如何？」——区间说的是**任务
期**，原来的 `_RANGE` 无条件命中，会把检索范围缩成"2021-2023 年发的文件"。现在区间后面
跟 `年间 / 期间 / 内 / 底` 等词时不当资料年；`2021—2023年的文件` 这种带资料标记的照旧筛。

**这两条改动在现有语料上的实测影响是 0**：

- 155 道题里**没有一道**使用年份区间写法（`_RANGE` 命中 0 次），所以时间那一条改变 0 道判定；
- 24 道点名地域的题里，每个被点名的城市**都有自己的文件**（宁波 5、绍兴 7、台州 4、湖州 2），
  没有一道落到"只有省标"的分支；7 道 geo 库外题仍然全部拒答。

也就是说，这两条是**为将来的语料准备的**，不是为这份语料。写清楚这一点，比报一个
"改动后 0 题变化、效果良好"要诚实。

**没做的**：专家建议的文档级结构化适用范围（地域层级/文件类型/实施日期/有效状态/
废止关系）。这需要动 `documents` 表与入库流程，属于下一阶段的独立工作，不是这一轮
能顺手带上的。目前"省级覆盖市级"是靠一张静态表 + 文件名判断，它解决的是"省标能不能
回答市里的问题"，解决不了"这份文件哪年作废、替代关系是什么"。

## 七、结论与下一步

**判官不进阻断，理由比上一轮更硬**：不是"误拒率高"，而是**这一层的单次测量不稳定**
（同输入两次 8~11 题翻转）。拿一个不确定的判据去拦截用户请求，误拦无法复现、也无法申诉。

可以继续的方向，按性价比排：

1. **多次采样取多数票**（3 次），先把这个判据变成可重复的测量，再谈它在什么口径下够用；
   现有 `judge-verdicts-*.json` 的 key 已经带候选摘要，加一列"第几次"就能存多票。
2. **只做提示，不做阻断**：v2 在温度 0 下误拒 4~5/122，把它的一句话带给用户
   （"这几条片段可能不足以回答"）成本很低；反过来按它阻断，会放过 3~5 次本该拒答的编造。
3. **扩 `near_topic` 的写法**：这一轮 21 道里仍有 3~5 道拦不住，其中 2 道是"片段给了上位
   要求、问句问具体经办"（找哪家机构、考什么证）。这类需要"同对象"判断，而判官现在的
   证据只有文件名与章节——给片段加上"条文号 + 适用范围"可能比继续改提示词更有效。

## 八、复现

```bash
# 候选与结论都有身份校验，换语料/换模型/换提示词/换温度会自动拒绝复用
python scripts/judge_sufficiency.py --judge v2 --k 8 \
    --dump eval/reports/judge-v2-t0-a-20261030.json

# 同一配置再跑一次，量这一层的抖动（这是本轮最该被复现的数字）
python scripts/judge_sufficiency.py --judge v2 --k 8 --rejudge \
    --verdict-cache eval/reports/judge-verdicts-v2-t0-b.json \
    --dump eval/reports/judge-v2-t0-b-20261030.json

# 复用 0 温度那两次的冻结候选（它的 src_sha 与当前代码一致，所以能过校验）
python scripts/judge_sufficiency.py --judge v2 --k 8 \
    --cache eval/reports/judge-hits.json --dump <out>.json

# 误拒拆两类（判官读走眼 vs 片段确实没有）
python scripts/diagnose_judge.py --dump eval/reports/judge-v1-k8-20261030.json --k 8
```

`judge-hits-k8.json`（三版对照用的那份）的 `src_sha` 是 `6c0bd19f`，**与当前代码不一致，
直接复用会被身份校验拒绝**——这是设计意图，不是缺陷：要复用它得回到产出它的那个代码状态。

原始结果：`eval/reports/judge-{v1,v2,v3}-k8-20261030.json`、`judge-v2-k8-run2-20261030.json`、
`judge-v2-t0-{a,b}-20261030.json`；误拒逐题见 `eval/judge-false-refusal-k8-20261030.md`。
