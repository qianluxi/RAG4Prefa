# RAG4Prefa

面向工程课题文档的检索问答系统：把 `.docx` / `.pdf` / `.md` 设计文档 / 申报材料 / 规范按章节建成知识库，
用**稠密向量 + BM25 混合召回**找依据，再让大模型**流式**给带引用的回答。

> 这是对 `qianluxi/milvus`（v2.8.6）的功能等价重写：同样能"上传文档 → 按项目/年份筛选 → 提问 → 得到答案"，
> 但去掉了 Word COM 绑定、全局可变状态和 4 300 行死代码。设计取舍见 `REFACTOR_PLAN.md`。

## 它解决了什么

| 常见坑 | 这里的做法 |
|---|---|
| 关键词过滤放在向量 Top-K 之后，召回被截断 | BM25 与向量**并行召回**，再用 RRF 融合 |
| 只按字数硬切，切出来的片段丢了章节上下文 | 按标题树切块，embedding 时带上完整层级路径 |
| 上传同一份文档重复入库 | `(项目, 文件名, 内容哈希)` 唯一 + 确定性 `chunk_id` + upsert |
| 统计数字恒为 0（读的键没人写） | **SQLite 是唯一事实**，计数一律 `COUNT(*)` |
| 多人使用时筛选条件互相串 | 筛选条件随请求传入，无全局状态 |
| "流式"其实是先跑完再逐词播放 | 大模型 token 流直通 SSE |
| 绑死 Windows + Word，进不了容器 | 纯 python-docx / pymupdf 解析，Linux/Docker 可跑 |
| pdf 没有样式表，章节结构全丢 | 按字号 / 加粗 / 行距反推层级；编号只定级，页眉页脚与页码剔除 |
| 换模型后新旧向量混在一个索引里，检索静默变差 | 模型 / 维度 / 归档 / 后端条数四方校验，不一致就拒绝写入与检索 |
| 更新文档时 embedding 失败，旧版本被顺手删掉 | 先算完新向量、**先写索引再切事实**；失败时撤回新增向量，旧版本照常可检索 |
| 索引残缺时系统照常返回"看起来正常"的答案 | `/api/chat` 在开流之前就 503；`/api/search` 明确报错；`verify` 能逐 id 定位差异 |

## 快速开始

```bash
python -m venv .venv
.venv\Scripts\activate            # Linux/macOS: source .venv/bin/activate
pip install -e ".[milvus,dev]"
cp .env.example .env              # 填入 embedding / LLM 的 base_url、api_key、model

python -m rag4prefa doctor        # 看后端、维度、缺哪些配置
python -m rag4prefa ingest "F:/project/课题/Ref" --project 立体聚落 --code kc2026 --year 2026
python -m rag4prefa serve --port 8000
```

打开 http://127.0.0.1:8000 ，左侧勾选项目/年份，直接提问。

### Windows 上一键启动：`start.bat`

装完依赖后双击根目录的 `start.bat` 即可。**默认端口是 8899**（不是 8000，也不是
Streamlit 的 8501），`start.bat 8000` 可改。窗口里看到

```
INFO:     Application startup complete.
```

才算起来了，这时再打开 `http://127.0.0.1:8899`。它不解压、不安装，只做四件事，
而这四件恰好是最容易做错的：

1. **`cd` 到脚本所在目录。** `R4P_DATA_DIR=data` 是相对路径，从别处启动会安静地
   新建一个空库——页面上显示"没有语料"，数据其实还在 `data\app.db` 里。
2. **用 `.venv\Scripts\python.exe`。** 系统 python 没装依赖。
3. **先探端口，再谈地址。** 端口已被监听时**不启动第二个实例**，而是把占着端口的
   PID 与进程名打出来，并告诉你可以打开哪个地址；失败一律 `pause`，窗口不会一闪
   而过。早期版本是先 `echo 地址` 再 `serve`，端口被占时 uvicorn 报 `[Errno 10048]`
   后窗口立刻关闭，用户只看到闪过一行地址、浏览器打开拒绝连接，反馈上来是"双击没
   启动成功"——地址只能代表"打算用"，不能代表"已就绪"。
4. **启动前跑一次 `doctor`**，缺 Key 或索引不一致就在这里报出来，而不是等点了
   提问才看到 503。

脚本不该被改的细节：它是 **GBK 编码 + CRLF**。`cmd.exe` 按系统代码页解析 `.bat`，
UTF-8 的中文不只是乱码——多字节字符会吞掉后面的命令字符（实测 `:fail` 被吃成 `ail`）。
仓库里靠 `.gitattributes` 的 `working-tree-encoding=GBK` 维持"存的 UTF-8、落的 GBK"。
上述约束由 `tests/test_start_bat.py` 钉住（顺序、失败必停窗、只认 LISTENING、编码）。

### 怎么停：`stop.bat`

优先在服务窗口里按 `Ctrl+C`。**点窗口右上角的 X 不算停止**：那只关掉了 `cmd`，真正
监听端口的是 `python.exe`（`.venv` 里那个是启动器，服务是它拉起的子进程），所以再
双击 `start.bat` 还是同一句"已经在监听"。这时双击 `stop.bat`：

```bat
stop.bat                :: 停默认端口 8899
stop.bat 8900           :: 停指定端口
stop.bat 8899 /force    :: 健康检查没回应（服务卡死）时强制停
```

它会先连 `/api/health` 看 `app` 字段，**只停自报 `rag4prefa` 的进程**；认不出来就只把
PID 和进程名打给你，不动手——按端口号杀进程，误杀别人家的服务只需要一次巧合。
这些判据由 `tests/test_processcontrol.py`（谁在听 / 是不是本程序 / 敢不敢动手）与
`tests/test_stop_bat.py`（参数透传、退出码、编码）钉住。

命令行也可以直接问答：

```bash
python -m rag4prefa ask "缓粘结预应力的张拉控制要点" --project 立体聚落 --answer
python -m rag4prefa reindex                  # 换 embedding 模型后全量重建
python -m rag4prefa reindex --project 立体聚落  # 只重建一个项目（维度不变时可用）
python -m rag4prefa verify                   # 逐 id 核对「片段 / 归档 / 索引」，出问题返回值非 0
python -m rag4prefa delete-doc --project 装配式规范 --file 某份文件.pdf   # 只删这一份（预览）
python -m rag4prefa delete-doc --doc-id 5d21ce18851caa8f --yes           # 按 id 删（真删）
python -m rag4prefa clear                    # 清空整库（预览影响面）
python -m rag4prefa clear --yes              # 真清空：项目/文档/片段/向量/任务
python -m rag4prefa ingest 某扫描件.pdf --project 装配式规范 --ocr auto   # 临时按页 OCR
python -m rag4prefa ingest 某旧文件.pdf --project 装配式规范 --ocr all --force  # 整份重识别
```

`--ocr` 只是**这一次运行**的覆盖，不回写 `.env`：试一次整份重识别，不该顺手把下次的默认
行为也改掉。取值 `off` / `auto` / `all`，与 `R4P_OCR_MODE` 同义。

**整批导入时请显式写 `--ocr off`。** `.env` 里 `R4P_OCR_MODE=auto` 的意思是"扫描件自动
逐页识别"，对单份文件很贴心，对一批 75 份就是按页计费 + 一小时起步——2026-10-28 实测：
不加 `--ocr`，45 份跑了 10 分 50 秒只过 3 份（第 4 份是 21 页无文字层的标准，四路并发在
逐页识别）；加上 `--ocr off`，同样 45 份 1 分 51 秒跑完，那 13 份进不来的按各自理由明确
报错。

**目录导入是递归的**（`_walk_corpus`），按 `0X_分类/子类/` 组织也能一次进去；以 `.` 开头
的目录整个跳过（`工程文档/.workbuddy/` 这类工作记忆不会被当语料收走），同一份文件被重复
指定只算一次。

### 视觉模型识别进来的文档要标出来

那 13 份"信息公开浏览专用"的标准（整页图 + 一行水印、或字体缺 ToUnicode）只能靠视觉模型
逐页读。实测质量够用——条文号、表格数值、检验方法逐格对得上——但**不是逐字保真**：
JGJ/T 491 的 3.1.10 少了「应采**用**绿色施工模式」里的"用"，JGJ/T 477 第 14 页末
「5.3.2 厨房家具的安装应符合下列规定：」整行消失、其下属 4 条被挂到了 5.3.3 名下。

所以识别过的页码会记在 `documents.ocr_pages`：

- `NULL` = 这份文档入库时还没有这一列，**不知道**有没有识别过；
- `[]` = 记过了，确实没有识别页（正文直接来自文字层）；
- `[1, 2, ..., 45]` = 这些页是识别稿。界面上会多一个「识别 N 页」的标记。

**NULL 与 `[]` 不能合并**：前者不能说"这是原文"，后者才能。这条列是事后追溯的唯一依据，
补都补不回来——识别稿和原文在检索结果里长得一模一样。

识别完跑一遍体检，它会把 500 页缩成十几处让人眼过一遍的地方：

```bash
python scripts/ocr_audit.py                            # 条文断档 / 表被引用却缺正文 / 认不出的字
python scripts/ocr_audit.py --md eval/ocr-audit.md     # 写一份报告
```

判据取的是文档自身的一致性：同一节里 `5.3.1` 后面直接 `5.3.3`，中间那段多半没识别出来；
提示词要求认不出的字用 `▢` 占位，所以 `▢` 的位置是**确定的**漏字。

**表号不查连续性**。规范和流水号不一样：条文号是人工从头到尾连续编排的，表号只是挂在
某一条下面的编号，没人规定条与条之间必须有表。GB 55038 的表 7.4.1 后面直接是表 7.4.5，
中间那三个编号是**条文号**——按连续性查会报"缺了 3 张表"，而那三条正文都在库里。
所以表只核一件事：**被引用了，却全文找不到它的表头**。图不核，图注没有表头可对照，
图号也天然不连续。4 份 / 135 页实测报 1 处，经人工回原页确认为真丢失。

**实际速率与费用**（SiliconFlow `Qwen3-VL-8B-Instruct`，150 dpi）：单页 1350 输入 + 437 输出
token，约 $0.0006/页；4 并发下**约 2~4 页/分钟**，135 页跑了 54 分钟。识别结果按页图哈希
缓存，失败重跑只补没识别的页，不重复付费——但也别随手 `--force`，那会得到"内容相同、
`chunk_id` 全变"的另一份文档。

`delete` / `delete-doc` / `clear` 默认都只**预览影响面**，加 `--yes` 才动手。`clear` 保留
`embed_cache`（同一段文字算过向量的缓存，删了只是下次多花一次钱）与服务端配置
（embedding 模型、后端身份）——后者描述"这个库怎么跑"，不是数据。

`reindex` 的语义：**先算完整个范围的新向量，再写 SQLite 归档，最后整体替换向量索引**；
中途失败不会留下半成品。只重建单个项目时不会清空其他项目的索引，但**必须沿用索引现有的模型**——
维度相同也不算数，两个模型的向量空间不能混。换模型走不带 `--project` 的全量重建，
维度变化会明确拒绝局部执行。详见下面「索引一致性」。

`verify` 与 `/api/health` 的分工：health 做廉价的条数比对（每次请求前都跑），
verify 做逐 id 的精确比对（要把索引主键全拉一遍，慢但能发现"条数相同、内容不同"）。

## 架构

```
api.py        FastAPI 路由（只做协议转换）
  ├── ask.py          检索 + 生成（混合召回 → RRF → 重排 → 流式）
  ├── ingest.py       解析 → 分块 → 向量化 → 写库；含 reindex / rebuild_store
  ├── consistency.py  索引一致性（模型/维度与归档是否自洽，能不能写、能不能查）
  ├── admin.py        项目/文档查询与删除
  ├── filters.py      问题 → Filter（规则优先，可单测）
  ├── chunking.py     标题树分块
  ├── repo.py         全部 SQL
  └── adapters/       embed / llm / ocr / vectors / rerank / query_expand / parsers（docx / pdf / md / 共用标题规则）
```

**数据分层**：SQLite 存事实（项目、文档、片段、任务、向量归档），Milvus 只是可重建的索引。
索引坏了或换后端，`rebuild_store` 直接从归档重建，**不需要重新调用 embedding**。

## 向量后端

`R4P_VECTOR_BACKEND` 三选一：

- `auto`（默认）：能用 Milvus 就用 Milvus，否则退化到 `numpy` 精确检索（结果可复现，靠 SQLite 里的向量归档）。
- `milvus`：Milvus Lite（单文件，无需 Docker）或 standalone，只改 `R4P_MILVUS_URI`。
  - Lite 不支持 HNSW 参数，统一 `AUTOINDEX`；切 standalone 后可自行换 `HNSW` 调参。
  - ⚠️ **Windows 上路径必须是纯 ASCII**：faiss 用窄字符 `fopen` 打开索引文件，中文目录名会让
    任何一次 `flush` / `release+load`（重建、换维度、重启后重开）直接失败。程序在打开集合前
    就会拒绝并说明原因，`auto` 会自动回退 numpy。要用 Milvus 就把 `R4P_DATA_DIR` 指到
    `C:/rag4prefa-data` 这类纯 ASCII 路径。Linux 没有这个限制。
- `numpy`：零依赖暴力余弦，十万级片段内延迟仍在毫秒级。

## API

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/health` | 后端、索引维度、模型一致性、缺失的凭据（不再静默降级）；`app` 字段供 `stop` 认身份 |
| POST | `/api/projects/{name}/documents` | 上传 docx / pdf / md（multipart）→ `job_id`；**不支持的格式逐个点名返回**，不静默丢弃 |
| GET | `/api/jobs/{id}` | 入库进度与逐文件结果 |
| GET | `/api/projects` | 项目列表（文档数/片段数为真实值） |
| GET | `/api/projects/{name}` | 详情 + 章节分布 + LLM 摘要（带缓存） |
| DELETE | `/api/projects/{name}` | 级联删除（SQLite + 向量） |
| DELETE | `/api/projects/{name}/documents/{doc_id}` | 删单个文件及其片段与向量；`doc_id` 不属于该项目时 404 |
| POST | `/api/admin/clear` | 清空整库；body 必须带 `{"confirm": "清空"}`，否则 400 |
| POST | `/api/search` | 非流式检索（调试与评估用） |
| POST | `/api/chat` | SSE 流式问答 |
| GET | `/api/llm-models` | 可选对话模型（白名单，逐个真调通过） |
| POST | `/api/credentials/verify` | 用给定 Key 各试一次，逐项回报 `embedding` / `llm` / `ocr` |

清空与删单个文件都**先清索引、后清事实**：反过来时若后端删不掉，归档已经没了、
`rebuild` 失去恢复源，"清空失败"就变成"数据被悄悄扔掉"。删完还要验后端条数归零，
不归零就报错且不动 SQLite——这条判据由 `tests/test_admin_clear.py` 钉住（含失败注入）。

SSE 事件：`meta`（生效条件、候选数、各阶段耗时）→ `token`* → `citations` → `done`；异常走 `error`。
`citations` 每项带 `page`——**该片段自己**的起始物理页码（1-based，PDF 才有；docx 为 `null`，
用章节路径定位）。它不是"本章节从第几页开始"：一节跨 4~29 页时，各片段按自己落在的页返回。

前端交互：答案里的 `[n]` 角标可点击，会滑出右侧「引用来源」抽屉并高亮对应片段；
抽屉默认收起，也可点气泡下的「查看来源」按钮打开。检索到生成期间气泡下方显示
「正在检索回答中…」的动态提示。

「项目管理」面板里三处入口：点项目行的「文件」展开该项目下每份文件（块数、年份、
解析状态），可逐份删除；行末「删除」删整个项目；面板底部「清空数据库…」先报影响面，
再要求手打「清空」两个字，服务端还要求同样的确认词——`curl` 也绕不过这道闸。
上传结束后会逐份列出结果：成功的块数、失败的原文报错、以及**格式不支持而被挡下的那些**。

## 测试与评估

```bash
pytest -q                                  # 553 项，全部离线；其中解析器金丝雀要本地语料（CI 上跳过）
python scripts/snapshot_corpus.py          # 先记下"此刻库里有什么"
python scripts/eval.py --dataset eval/dataset.jsonl --save
python scripts/eval.py --dataset eval/dataset.paraphrase.jsonl --save
# 并行改写通道的对照（冻结扩展串，权重视为一个自变量）：
python scripts/eval.py --dataset eval/dataset.paraphrase.jsonl \
  --expand-from eval/expansions/paraphrase-20261028.jsonl --expand-parallel \
  --modes dense,sparse,hybrid,rerank,hybrid_parallel,rerank_parallel --save
# 受控词表（公众表达→规范用语）：术语作独立通道 + 重排读「原话 + 术语串」
python scripts/eval.py --dataset eval/dataset.paraphrase.jsonl \
  --term-map rag4prefa/terms/public_to_standard.v2.json --term-form joined --term-rerank append \
  --modes hybrid,hybrid_parallel,rerank,rerank_parallel --save
```

生产链路上同一个开关叫 `R4P_TERM_MAP`（留空 = 关闭），形态与重排查询由
`R4P_TERM_MAP_FORM` / `R4P_TERM_RERANK` 决定，默认值与评估里验过的组合一致
（`joined` + `append`）。见下文「受控词表接进生产链路」。

**评估数字只有在语料身份确定时才有意义，所以先出快照。** `snapshot_corpus.py` 从数据库导出
`eval/corpus-snapshot.json`：文档数、片段数、全量 `chunk_id` 与整体指纹，不依赖源文件
（补语料时旧文件会被删，靠重新解析拿不回当时的指纹）。评估报告读它并核对，对不上就显式写
「语料已变化，与旧报告不可直接比较」。

评估集分三份，**不要混成一个平均数**：基础 31 题（按工作里的说法提问）、口语 50 题（只描述
意图、不用原文术语）、库外 6 题（上海/北京/日本/江苏/深圳 + 一道语料确实没有答案的"多久能住"）。
下面这一版（HANDOFF 记为第八版）把**两路候选的融合方式**从等权 RRF 换成了「本路标准化后
加权求和」（`fusion=zscore`，见 `ask.fuse_scores`）。同一份语料快照（75 份文档 / 2560 片段，
`ids_sha = 208ec1576dfc11cc`）、同一套参数（`Qwen/Qwen3-Embedding-0.6B` 1024 维，chunk
80~480 token，`recall_k=50`，`candidate_k=50`，`rrf_k=60`，重排
`Qwen/Qwen3-Reranker-0.6B`），**两版同一天前后脚跑**：

| 召回方式 | 基础 31 题（rrf → zscore） | MRR | 口语 50 题（rrf → zscore） | MRR |
|---|---|---|---|---|
| dense（纯向量） | 0.710 → 0.710 | 0.583 → 0.583 | 0.600 → 0.600 | 0.418 → 0.418 |
| dense_rerank（纯向量 + 重排） | 0.806 → 0.806 | 0.625 → 0.625 | 0.680 → 0.680 | 0.558 → 0.548 |
| sparse（纯 BM25） | 0.774 → 0.774 | 0.610 → 0.610 | 0.340 → 0.340 | 0.269 → 0.269 |
| hybrid（向量 + BM25 + 融合） | 0.774 → **0.871** | 0.576 → 0.688 | 0.460 → **0.640** | 0.317 → 0.388 |
| rerank（混合 + 重排） | 0.839 → **0.871** | 0.655 → 0.662 | 0.700 → 0.680 | 0.550 → 0.546 |

前三行是**对照组**：它们不经过融合，两版逐题一字不差（`dense`、`sparse` 名次变化 0 题）。
所以后两行的差值只可能来自融合这一步。

四句话读完这张表：

1. **融合从"拖后腿"变成"有增益"。** 换之前 `hybrid` 在口语集上比纯向量低 0.140
   （0.460 vs 0.600），施工维护组 0/7；换之后高 0.040（0.640 vs 0.600），两套题集都涨
   （基础 +0.097、口语 +0.180），逐题是赢 10 输 1 / 赢 3 输 0，不是"救一题丢一题"的交换。
2. **开着重排时，50 深池上两者几乎无差别**（口语 0.700→0.680 是 1 题噪声、基础 +1 题）。
   原因不是融合没用，而是**重排对池内每条独立打分，池内顺序不影响它**，只有"gold 有没有
   进池"才影响；池深 50 时两版的池内覆盖率一样（口语都是 41/50）。
3. **生产默认池深是 25，那里差别是实的**（`candidate_k = max(recall_k//2, top_k*3)`）。
   同样走重排：口语 0.640 → **0.720**（赢 4 输 0），基础 0.839 → **0.871**（赢 2 输 1）。
   拿 50 深池的报告说"融合对重排没用"，会把生产场景的收益读丢。
4. **口语 50 题的绝对数不能与第四版 15 题的 0.400 比。** 15 题是"先出题、再满库找、
   找不到就认"；新加的 35 题里 31 题的 gold 在出题当时已经出现在检索候选里（可见性偏差），
   难度偏易。要比只能比同一批题在同一时间、不同配置之间的差值。

**重排的绝对值会漂。** 上一版报告里 `dense_rerank` 是 0.839，这一版两行都是 0.806——
这一行不经过融合，代码也没动，唯一能变的是重排服务自己的输出（同一天重跑两版均复现
0.806；单题连跑 4 次同进程内一致，跨时段不同）。所以任何"比上一版涨了多少"的说法都
必须在同一天把两个配置各跑一遍再作差；跨天的两个绝对值相减，差里至少含 1 题的噪声。

**融合为什么这么改**（细节见 `ask.fuse_scores` 的 docstring）：口语集 50 题里有 17 题的
gold 只有稠密这一路找得到，BM25 回的是另一批不相干的片段。两路候选几乎不相交时，等权
名次求和退化成"把展示位对半分"——dense 的第 k 名被挤到第 2k 名。单题实测「卫生间地面
要不要往地漏那边找坡」：gold 在 dense 第 1、BM25 不进前 50、融合后第 22。算术上
`1/61≈0.0164` 打不过 `1/91+1/90≈0.0220`。改成"各自在本路内部标准化后加权求和"之后，
两路按"这一路认为它有多突出"分配话语权，不再白送一半展示位。
`tests/test_fusion.py` 用构造数据钉住这条（含 6 条变异用例）。

前几版报告留在 `eval/reports/`：从这一版起文件名带 `-fusionrrf` / `-fusionzscore`，
更早的报告没有这个后缀（那时只有 rrf 一种），数字不要跨这两类直接比大小。

**`doc_year` 是过滤条件，不是展示字段。** 问句里出现年份时（"2025 年的补贴包含什么"），
检索会把候选收窄到那一年；年份为 NULL 的文档**一条都匹配不上**，而界面看起来完全正常。
2026-10-28 两版语料都撞到：52 份全为空，整库重导后的 62 份又全为空——`ingest` 不带 `--year`
写的就是 NULL，它不会去猜。回填用 `python scripts/backfill_doc_year.py`（先预览）→
`--apply`（只改年份，不重算向量）：

```bash
python scripts/backfill_doc_year.py           # 只打印推断结果与依据（文件名 / 发文日期 / 来源 URL）
python scripts/backfill_doc_year.py --apply   # 写库
```

推断不出的会**保持 NULL** 并单独列出来——写一个猜的年份会让过滤悄悄收窄，比缺年份更难发现。

标注改动后要跑 `python scripts/relabel_eval.py --db data/app.db --write`：它按每题的正文锚点
重算 `gold_chunk_id`。**改了解析器就必须重跑**——`chunk_id` 是内容寻址的，章节路径变一个字
id 就全换，旧标注会静默失效（评估照样跑完，只是 Recall 莫名变低）。

「解析器改没改」这件事由两道记录分开守，别混：

| 记录 | 谁来写 | 守什么 | 什么时候重跑 |
|---|---|---|---|
| `eval/corpus.json` | `scripts/build_manifest.py`（从库导出） | 标注时那批语料是什么 | 语料换血 / 标注之后 |
| `eval/corpus-snapshot.json` | `scripts/snapshot_corpus.py`（从库导出） | 上次出报告时库里有什么（含全量 id） | 入库、删文档之后，出报告之前 |
| `eval/parser-canary.json` | `scripts/build_manifest.py --canary`（重新解析 7 份样本） | 当前解析器对这些样本输出什么 | 有意改了解析判据之后 |

金丝雀只取 7 份（合计约 3 秒）：全量 52 份重解析实测 106 秒，且其中 5 份当初是开着 OCR
入库的、纯离线本就复现不出来。它报的是"解析器变了没有"，不是"哪份文档变了"。

**源文件被删之后**，前两道"重新入库再比对"的路走不通了。此时由
`tests/test_eval_dataset.py::test_dataset_gold_survives_without_source_files` 兜底：拿快照里的
全量 `chunk_id` 离线判定 gold 是否还在语料里。少了这道守护，标注过期会以"跳过"而不是"失败"的
姿态消失，看测试摘要根本注意不到。语料目录也不可能总是扁平的——按名字找源文件走
`snapshot.locate_corpus_file()`（原名两份时它报错而不是挑一份），否则语料一分类，整套用例就
整体静默跳过（2026-10-28 实际踩到）。

报告头部现在固定包含：坐标系（模型/维度/chunk 参数/`recall_k`/`rrf_k`/重排）、语料快照与
`ids_sha`、数据集哈希与题数、生成时间、代码提交与工作区状态。**这六项任一不同，前后两份就不可比。**
`--save` 按 `<数据集>-<日期>-<ids_sha 前 8 位>.md` 命名，同名即同语料。历史报告在
`eval/reports/archive/`，保留是为了留下"当时的结论是什么"，不再当基线。

CI（`.github/workflows/ci.yml`）在每次 push / PR 上跑同一组命令：`ruff check rag4prefa tests scripts`
→ `pytest -q`。全部离线，不需要任何 Key。

`scripts/eval.py` 默认输出五行对照——`dense`（纯向量）、`dense_rerank`（纯向量 + 重排）、
`sparse`（纯 BM25）、`hybrid`（向量 + BM25 + RRF）、`rerank`（混合 + 重排）——这是
"混合检索和重排各自带来多少收益"的量化依据。另外两行 `hybrid_parallel` / `rerank_parallel`
是并行改写通道，**默认不跑**，要用 `--modes` 显式点名。
**没配 `R4P_RERANK_URL` 时报告会显式写「未启用重排」**，而不是让 `rerank` 一栏悄悄等于 `hybrid`
（那样读者会把两行差异当成重排的收益；曾经就因为两行用了不同深度的候选池，差出过一个 +0.033）。

重排是**可选增强**：配了 URL 默认开启，也可以 `--no-rerank` 显式关掉。它多一次网络往返，
换来的是上面改写集那 0.10 的 Recall。`/api/health` 的 `rerank_configured` 会告诉前端
"这台机器到底有没有重排"，免得界面上留一个勾了也不生效的开关。

指标定义（写死在 `tests/test_eval_metrics.py` 里，不接受含糊）：

- 三个指标共用**同一个 gold 集合，单位是 chunk**。
- `Recall@k = |TopK ∩ Gold| / |Gold|`，分母是**标注的相关项总数**，不是返回条数。
- `MRR` 取第一个相关结果的倒数排名。
- `nDCG@k` 按二值相关性计算，IDCG 用标注的相关项总数构造理想排序。
- 报告里每种召回方式**单独列一行有效样本数**：某个方法在部分题上失败时，均值建立在不同的
  题目集合上，不能拿"总题数"糊过去。

标注优先用 `gold_chunk_ids`（无歧义）；图省事可以写 `gold_snippets`，脚本会把每个片段解析成
**该题筛选范围内**包含它的全部 chunk 再计入 gold——不按范围解析的话，别的项目里出现的同一段
文字也会被算成相关项，而本题根本召回不到，Recall 会被系统性压低。解析不设上限（不静默截断），
写错的 `chunk_id` 会被剔除并写进报告的数据问题里。

## 索引一致性

一个索引里只能有一套向量空间。判断依据是**声明 + 事实 + 逐 id 对应**，任一不满足就**拒绝服务而不是降级**：

- `meta.embedding_model` / `embedding_dim`：上一次成功建索引时声明的模型与维度；
- `vectors.model` / `dim`：归档里每一行实际是谁算的；
- 片段与归档的逐 id 对应（缺向量、孤儿向量、模型未标注都算不一致）；
- 后端实际条数与归档条数的交叉校验（归档对、Milvus 少写几条，只查 SQLite 是看不出来的）。

出现任意一条，增量入库、局部 `reindex`、检索都会拒绝；`/api/health` 的 `index.consistent` /
`index.issues` 如实报告，`ok=false` 时先看这里。换模型只能全量 `reindex`（不带 `--project`），
局部重建必须沿用现有模型。

另外两条准入，被拒绝时同样是"什么都不改"：

- **库里有内容，就必须有一个被确认过的活动后端**（`meta.vector_backend`）。没有登记值意味着
  确认动作试过并失败了，不是"还没配"——此时查询（HTTP / CLI / 评估）、普通入库、删项目一律拒绝，
  `python -m rag4prefa rebuild` 从归档重建并登记即可恢复。`doctor` / `verify` / `rebuild` /
  全量 `reindex` 保留入口，否则没法修。
- **后端身份 = 类型 + 存储位置**：`meta.vector_backend_id` 记 `milvus|<uri>|<collection>` 或
  `numpy`。共用一份 `app.db` 的进程必须用同一份 `R4P_MILVUS_URI` / `R4P_MILVUS_COLLECTION`，
  否则会在第一次比对时被指出来（而不是两边各写一半、谁也查不到谁）。

`chunk_id` 是**内容寻址**的（`doc_id + 章节路径 + 正文哈希`），不是位置序号：同一 id 必然是同一段正文。
这是"先写索引、后切事实"能安全的前提——改一段不会让后面所有片段换号，也不会出现"新向量配旧正文"。

## 口语问句的术语通道（可选，默认关闭）

公众说法与条文用词常常不是一回事：「墙上挂电视和吊柜会不会掉下来」在语料里查不到，
而条文原话「墙面悬挂较重物体」「专用连接件」一查就进前 5。这一层是一张**人工维护、
每条带出处**的查找表（`rag4prefa/terms/`），把口语说法映射成规范术语，命中后以两条
通道进入检索：

- **召回**：术语串作为**独立通道**参与融合，原话那一路一条都不动。拼进原话的那种写法
  已被证伪（0.400 → 0.467，5 道目标题一道没救回）：原话的排序跟着变，术语反倒成了干扰词。
- **重排**：重排器读「原话 + 术语串」。只读术语串会打坏**本来已排第 1** 的题——15 题实测
  原话 11/15、纯术语串 12/15、原话 + 术语串 14/15。

开关（默认全关；留空即与没有这一层时完全一致）：

| 变量 | 默认 | 说明 |
|---|---|---|
| `R4P_TERM_MAP` | 空（关闭） | 词表 JSON 路径 |
| `R4P_TERM_MAP_FORM` | `joined` | 术语拼成一串；`terms` = 每个词一条通道 |
| `R4P_TERM_RERANK` | `append` | 重排读「原话 + 术语」；`terms` 只读术语；`none` 只读原话 |
| `R4P_TERM_REWRITE_WEIGHT` | 0.5 | 术语通道的融合权重（原话恒为 1.0） |

2026-10-29 在 50 题口语集上量过（报告 `eval/reports/…-termmap-public_to_standard.v2-joined-w05-rerankappend-fusionzscore.md`）：

| 召回方式 | 不开词表 | 开词表 |
|---|---|---|
| `hybrid`（融合候选） | 0.640 | 0.620 |
| `rerank`（融合 + 重排） | 0.680 | **0.760** |

收益**严格等于被覆盖的题**：28 条词覆盖 15/50，覆盖组 0.667 → 0.933（赢 4 输 0），
未覆盖的 35 题名次全同；`hybrid` 那行 -0.020 是一题的量级（单次运行有 ±1 题地板）。
`joined` 与 `terms` 两种形态在同一天各跑一遍：**Recall 逐行相同**，名次上 2 题前移、
1 题后移，所以生产取 `joined`（少 N−1 次 embedding 往返）——术语串在问句之间高度重复，
第二次起命中 `embed_cache`。

两个边界要写清楚：①**它只覆盖口语说法**，专业问法集上未命中就等于没有这个功能，收益为 0；
②它是按问法索引的**查找表**，不是知识层——条数翻 3.5 倍净增益没有增加，泛化仍未证明
（见下文「已知局限」）。运行 `/api/health` 能看到开关状态与命中条数，`/api/chat` 的
`meta` 事件带 `terms` 与 `term_entries`（命中哪条、被哪几个词触发），界面状态栏会显示
「术语通道 …」。配了路径却没把词表交给检索会直接报错，坏词表则降级并写进健康检查——
这两件事都不允许静默发生。

## 多用户与 API Key

前端右上角「API 设置」可以让每个人填自己的 Key，存在**本机浏览器的 localStorage**，
之后自动随请求带上；换人只需在列表里点一下，不用重新输入。服务端只在请求期间持有 Key，
不落库、不写日志。

请求头约定（curl 或脚本直接调也能用）：

| 头 | 含义 |
|---|---|
| `X-R4P-User` | 用户名，仅用于显示；中文需 `encodeURIComponent`（HTTP 头只能是 ASCII） |
| `X-R4P-Embedding-Key` | 入库与检索用的 Key |
| `X-R4P-LLM-Key` | 生成答案用的 Key |
| `X-R4P-LLM-Model` | 选哪个对话模型，取值须在 `GET /api/llm-models` 返回的清单里 |
| `X-R4P-OCR-Key` | 扫描件识别用的 Key（第三家服务，与前两把都不通用） |
| `X-R4P-Admin-Token` | 管理口令：清空库、删项目、删文件要它（与额度无关，只管"谁有权删"） |

**默认各付各的**：`.env` 写 `R4P_ALLOW_SERVER_KEY_FALLBACK=false`，本文件里的 Key 只属于
服务端主人，别人的请求一律不回落。校验按**接口实际需要的那把 Key**逐个进行：

| 接口 | 必须自带 |
|---|---|
| 入库 / 检索 | Embedding Key |
| 问答 `/api/chat` | Embedding Key + LLM Key |
| 扫描件入库 | **Embedding Key + 视觉模型 Key** |

上表是"这个接口最少要有哪些"，不是"三把都得填"：只带 embedding 就是"入库花我的额度"。
**扫描件的门槛比普通文件高一把**：上传端点先要 Embedding Key（识别完还得切块、算向量、
写索引），真正走到某一页需要识别时再要视觉模型 Key（按页计费）。所以只填
`X-R4P-OCR-Key` **不够**——请求会先在上传入口被 embedding 校验拒掉；反过来只填
embedding、不填视觉模型，结果是"Word 与带文字层的 PDF 照常入库，扫描件报无法入库"。
两份都缺，先看到的是 401。清单以外的模型名不会报错，而是静默回落到服务端默认——
避免浏览器里存着已下线的名字时整个请求失败。

`R4P_ALLOW_SERVER_KEY_FALLBACK=true` 只适合单机自用（CLI、curl、内网演示）：那时任何人
打开页面都能白用你的额度，账单只有一个人付。

**"验证没通过"的 Key 不会被发出去。** 点「保存并验证」之后，三个角色各自的结果会记在本机：
通过的 Key 随请求发送，没通过的只留着等修改（改好再验一次才启用），列表里也会标出
"哪几项未启用"。所以"填了但报错"和"没填"在服务端看来是一样的——不会出现"验证时已经
告诉你这把不通，真跑的时候又把它发出去，最后在异步任务里失败"这种自相矛盾的行为。

**为什么 embedding 模型不能选、对话模型可以选**：embedding 决定向量空间。若允许每人自选，
同一批文档里就会并存两套向量——余弦相似度照样算得出来，只是语义错位，检索结果看起来正常
却不可信。所以 `embedding` 的 `base_url` / `model` / `dim` 由服务端 `.env` 统一决定。
对话模型只读"已检索到的片段"、不参与建索引，换它只影响措辞与推理深度，因此开放给用户。
`/api/credentials/verify` 会真调一次并回报维度，与服务端建库时的维度不一致会直接拒绝。

预设的对话模型都是逐个真调通过的（`Qwen3.5-35B-A3B` / `Qwen3.8-Flash-Next` /
`Qwen3.8-27B` / `Qwen3.5-122B-A10B`）。**不要直接拿 `/v1/models` 的结果去渲染下拉**：
那个目录里 DeepSeek V4 全系、MiniMax-M3 等一大半调用会返回 `has no provider supported`。

**这不是身份认证**：知道用户名的人可以填自己的 Key 顶替，服务端不校验密码，取回 Key 也不设防。
它解决的是"几个人分摊额度、各自记住自己的 Key"，不是"谁有权访问知识库"。

**也还没有用户管理**：没有登录态、密码、禁用、配额与审计。要做成真正的多租户，得把 Key 改成
服务端托管（加密存储、可吊销、可审计），加上登录与权限，并把上传、删除一起收进鉴权。

**销毁入口有第二道门**：下面三条接口不可撤销，`confirm: "清空"` 只防手滑、不是授权凭据，
所以它们要过管理口令（请求头 `X-R4P-Admin-Token`，取值来自 `.env` 的 `R4P_ADMIN_TOKEN`）。

| 接口 | 后果 |
|---|---|
| `POST /api/admin/clear` | 清空全库（文档、片段、索引与归档） |
| `DELETE /api/projects/{项目}` | 删掉整个项目 |
| `DELETE /api/projects/{项目}/documents/{id}` | 删掉单个文件 |

规则三条：**配了口令**就校验（缺头、错头都 403，定长比较，但两种提示不一样：没带会说去哪儿填、
怎么保存，带错才指向 `.env` 里那份值）；**没配、又是各付各的部署**
（`R4P_ALLOW_SERVER_KEY_FALLBACK=false`）就**直接 503**——宁可删不了，也不让访客清库；
**没配、且是单机演示**则放行，那时打开页面的人就是主人。页面「API 设置」里有"管理口令"一栏，
填同一个串、点「保存管理口令」即可（只存浏览器）；改过 `.env` 要重启服务，页面里也要重新保存一次。
CLI 的 `python -m rag4prefa clear` 不受影响。

**如果被拒而页面里找不到"管理口令"这一栏**，说明拿到的是改版前的缓存页面——强制刷新
（`Ctrl+F5`）即可；首页现在带 `Cache-Control: no-cache`，之后不会再犯。

这仍然**不是账号体系**：一把共享口令、没有输错次数限制、也没有审计。要区分"谁能看 / 谁能删"，
还是得做登录与权限。额度那层已经收口（不代付之后匿名请求用不了你的 Key），删库这层现在有门，
但门是同一把钥匙。

## OCR：扫描件怎么进来

代码默认关闭；本仓库的 `.env` 已开 `auto`。开启后，**没有可用文字层的页**会渲染成图交给
视觉模型，其余页仍走字号判据。

**扫描件按页计费，所以它同样遵循上面的"各付各的"**：`.env` 里的 `R4P_OCR_API_KEY` 只是
服务端主人自己那把；别人要用扫描件，得在「API 设置」里填自己的视觉模型 Key（与 embedding
同一站点的 Key 可以两处复用），**同时还要有自己的 Embedding Key**——识别完的文字要落进库，
那一步也要花钱。缺任一把就**无法入库**：任务会失败并说明原因，文件不进索引，
索引与归档一个字节都不动。绝不静默跳过，也绝不悄悄用服务端那把替他付。

页头标签区分两种状态：`OCR 待配置` = 该你填（本部署不代付），`OCR 未配置` = 服务端没配好
（单机演示模式下没填 `.env`）。

```bash
# .env
R4P_OCR_MODE=auto                     # off / auto / all
R4P_OCR_BASE_URL=https://api.siliconflow.com/v1
R4P_OCR_API_KEY=sk-...
R4P_OCR_MODEL=Qwen/Qwen3-VL-8B-Instruct
```

为什么是视觉模型而不是传统 OCR：Tesseract / PaddleOCR 要落一份模型到磁盘（与"不引入本地
模型"的约束冲突），而且只给**文字**，不给"这是一级标题""这是一张表"——后者才是切块依赖的
东西。视觉模型一次调用同时给出文字、层级与表格结构，代价是每页一次请求。

实测（2026-10-27，一份 24 页的上海 250 号公文，整份扫描）：

| | |
|---|---|
| 耗时 | 23 页 × 约 18 秒 ÷ 4 并发 ≈ 3.5 分钟（串行要七分钟） |
| 产出 | 48 节 / 57 块，章节路径到「一、实施范围 >（三）工业建筑类项目」 |
| 内容 | 与原文逐条对上（8000 平方米、15%、沪府规〔2021〕18 号、浅圆仓…） |
| 缺页 | 第 23 页识别后仍无文字（印章页），在任务汇总里点名报出来 |

**识别结果按「页图哈希 + 模型名 + 提示词版本」缓存在 `ocr_cache`。** 这不只是省钱：
视觉模型输出不确定，同一页两次识别会差几个字，而 `chunk_id` 是内容寻址的——没有缓存，
`--force` 重入库会把同一份文件变成"另一批 id"，旧向量原地成孤儿，`verify` 还查不出
（它只比 id 集合是否自洽）。所以缓存是这一步**可重入的前提**，也是"失败重试很便宜"的原因：
100 页里第 87 页失败，重跑只补那一页。

代价要说清：一页十六七秒、一次调用一份钱，所以 `R4P_OCR_MAX_PAGES`（默认 200）是账单闸门
而不是性能限制——超了直接拒绝并说清怎么放开，不做"先跑一半"。

### 为什么没有"免费档"

曾经做过一版可切换的免费档（硅基流动国内站 `PaddleOCR-VL-1.5`，官方计价项 ¥0），
2026-10-27 用一份 24 页扫描件实测后**整个移除**。证据留在这里，免得以后有人再试一遍：

| | 付费 `Qwen3-VL-8B` | 免费 `PaddleOCR-VL-1.5` |
|---|---|---|
| 24 页耗时 | 3 分 39 秒（4 并发） | 17 分钟只跑完 8/24（2 并发） |
| 单页耗时 | 15~18 秒 | 普通页 55 秒，公式页 **250 秒** |
| 可用性 | 23 页识别、1 页空白（印章页），48 节 / 57 块 | **8 页里 2 页是伪造内容** |

两页坏得很具体：一页是纯中文正文（无表格无公式），却被整页编成英文的
"The area of a circle is given by A = πr²"，150/120/100 dpi 三个分辨率**全部复现**；
另一页退化成 `1. 1. 2. 3. 4. …` 的数字重复，一路顶到 `max_tokens`。
换另一个免费候选 `deepseek-ai/DeepSeek-OCR` 更糟：一页满屏 `}}}]`，一页 0.9 秒只回 3 个字符。

关键不是"准不准"，而是**伪造正文会被切块、写向量、被引用成答案，而且不报错**。
RAG 系统里这是最坏的一类失败——它不崩溃，只是胡说。降低 dpi、换提示词、加 `max_tokens`
限制都没用（三档分辨率输出同一段伪造内容），所以没有"调一调还能用"的空间。

现在的策略只有一条：

- 扫描件只走 `.env` 里的 `R4P_OCR_*`（默认国际站 `Qwen3-VL-8B`，一份 24 页约 1.4 角）。
- **没配好就不处理扫描件**。错误消息以 `【需要配置视觉模型】` 开头，网页会在任务输出下面
  弹一个「配置视觉模型」按钮直通设置；用户不配，这份文件就进不来——不会被静默跳过。
- 用户可以在「API 设置」里填自己的视觉模型 Key（请求头 `X-R4P-OCR-Key`，不落库）。
  模型由服务端锁死：换模型会让同一份文件重新切块、换一套 `chunk_id`，代价远大于收益。

## 已知局限

- **收 `.docx` / `.pdf` / `.md`**。同名的 `.doc` 必须先用 Word「另存为」`.docx`：老式 `.doc`
  是 OLE 二进制（不是 zip 包），解析要额外依赖。上传时这类文件不会被静默跳过——接口会逐个
  返回文件名与"怎么办"，页面也会列出来（`skipped` 字段）。`.html` 与图片不收：网页存档的
  正文与导航混在一层 DOM 里，切块的边界定不准，抓取时转成 md 比在入库时猜更可靠。
- **md 的结构从 `#` 来，没有 `#` 时从编号来**（`一、` / `（一）` / `1.1`，与 pdf 共用同一套判据）。
  两条清洗规则都是"整行"级别的：网页模板行（索引号 / 发布机构 / 浏览次数 / 打印关闭）与
  它们的值（日期、流水号）整行丢弃；行内只去 `**`、反引号与图片语法。**不做智能去导航**——
  判错的代价是正文消失，而正文消失在这个系统里不可见（用户只会以为"检索没抓到"）。
  编码先按 UTF-8（含 BOM）读，失败退 GBK：抓取工具留下的 GBK 文件很常见，整份拒收会连
  可用的正文一起扔掉。
- 解析是基于排版结构的启发式：报表类文档正文在表格里，已支持；但图片、文本框内的文字不提取。
- **扫描件默认进不来，开了 OCR 才能进**（`R4P_OCR_MODE=auto`，默认 `off`）。三种坏法分开报：
  - **整份没有文字层**（扫描件、图片导出）→ 明确报错，不带 OCR 时不会静默入库；
  - **字体缺 ToUnicode 映射**——方正书版等排版软件常见，文字层里存的是字形编号，
    取出来是 `!"#$%&'()*` 这样的串，任何工具都无法还原成汉字，只能换版本或交给 OCR；
  - **混合型**：封面扫描 + 正文可复制的公文，或中间插了几页扫描的审批表。
    以前这类文档会**静默丢掉扫描的那几页**（整份闸门看全文，扫描页在逐页取文本时取不到
    任何东西），入库结果里看不出少了内容；现在会把"第 3、7 页没有文字层"写进任务汇总，
    开 OCR 则自动补上。判据从"整份文档"改成"逐页"，这是 2026-10-27 的改动。
- **「有文字层」不等于「有正文」**。住建部「信息公开浏览专用」的 pdf 是整页扫描图上面
  叠一行水印（「住房城乡建设部信息公开　浏览专用」），一页 37 个字符、全是汉字：字符数、
  汉字占比、乱码三道判据**一道都拦不住**，45 页会被拼成一节假正文入库。判据因此改为看版面
  ——图片**合计**覆盖 ≥ 60% 且文字 ≤ 120 字即判定为扫描页（实测水印页覆盖 1.00、正常文档
  0.00；水印页由多张图拼成，判单张最大覆盖会全漏）。这类文件不开 OCR 会**明确拒绝并说明
  "文字层里只有水印"**，而不是静默入库。
- **OCR 出的层级比文字层更依赖编号**。视觉模型只回答"这一行像不像标题"，"第几级"仍由
  `text_heading_level()` 按 `一、`/`第X章`/`4.2.1` 判——与字体那条路共用同一套规则，
  所以两种来源的层级不会各走一套。**没有编号、又不加粗**的标题在 OCR 页上认不出来，
  会退化成正文（内容不丢，只是章节路径缺一层）。
- **OCR 输出不可复现**：同一页识别两次会差几个字。所以识别结果按"页图哈希 + 模型名"
  缓存在 `ocr_cache` 里——这不是省钱优化，是让 `chunk_id`（内容寻址）保持稳定的前提。
  换了模型或改了提示词，缓存自动失效、整份重算。
- **PDF 的章节层级是反推出来的**：依据字号、加粗、行距与编号，不是文档自带的样式表。
  标题与正文同字号、又不加粗、还不用编号的排版，会退化成一节（内容不丢，只是没有层级）。
  表格识别依赖框线，无边框的"空格对齐表"会被当成正文。
- token 用字/词估算而非真实 tokenizer，分块边界与模型实际计数有误差（阈值留了余量）。
- 未做多轮对话改写：追问需要带上上下文关键词，否则召回会偏。
- **单轮口语术语扩展（`--expand`）首版被证伪，修好实验设施后重跑依然成立**。
  `adapters/query_expand.py` 用 LLM 把口语问句扩成「原话 + 术语」再检索，目标是把
  「会不会掉下来」映射到「悬挂较重物体应采用专用连接件」。对照实验（口语集 15 题）只让
  dense 从 0.400 升到 0.467，而 5 道「词表鸿沟」题**一道都没救回**——逐题看只把
  「吊顶装灯风机」拉回前 5，同时把「装修完多久能住」挤出去（该题标注本身有问题，
  见 `eval/annotation-audit-20261028.md`），其余只是名次挪动。原因是扩展词里「吊柜/电视」
  这类从原话继承的干扰词，在语料里的频率比术语更高，反而把正确片段挤出候选池。
  更麻烦的是**扩展本身不确定**：同一份数据跑两次，15 道题的扩展词没有一道相同，
  hybrid 因此在 0.333 与 0.400 之间跳——±0.067 就是一题的权重，与要测的效应同量级。
  所以做对照必须冻结扩展串：
  `python scripts/eval.py --dataset eval/dataset.paraphrase.jsonl --expand-from eval/expansions/paraphrase-20261028.jsonl --save`。
  用同一组扩展串比较「重排读原话」与「重排也读扩展串」（加 `--expand-rerank`），
  逐题 gold 排名完全一致：**扩展改善不了重排判断**。扩展因此**默认不参与生产链路**，
  只作为 `retrieve()`/`search()` 的可选参数与评估的实验开关保留。
- **并行改写通道（`--expand-parallel`）解决了稀释，但没跨过鸿沟**。原话独立查一路、
  改写串各查一路，按权重融合（`rewrites` + `rewrite_weight`，原话恒为 1.0），
  基线行（dense/sparse/hybrid/rerank）与不改写时**逐字一致**——变量终于只有"有没改写"一个。
  三个权重 0.3/0.5/1.0 下：`hybrid` 0.333 → `hybrid_parallel` 0.400 / 0.333 / 0.333，
  涨的那一次只多救回 **1 题**（吊顶装灯风机，拼串版也能救回）；`rerank_parallel`
  与 `rerank` 完全相同。**5 道词表鸿沟题仍 0 救回。**
  逐通道归因给出了原因：4 道题的 gold 在改写池里（15~35 名），4 道题**两路都没有**。
  后者是关键——用规范原文的搭配（「专用连接件」「不含电器设备」「参照执行」
  「维修更换」「隐蔽工程验收」）单独查，gold 排 **1/1/5/6/6**；而 LLM 给的近义概念
  （「锚固」「照明灯具」「既有建筑」「更换」「检验批」）最好也只有 12~36 名。
  **差距不在检索算法，在术语从哪来**：LLM 擅长把口语归到哪一类意图，不擅长说出
  条文里的那个固定搭配。下一步是受控的「公众表达 → 规范用语」对照表，而不是继续
  调权重、池深或换模型。注意这条链路**不能真并发**：所有读路径共用一条 sqlite 连接，
  多路并发会 `InterfaceError` 且只丢一路（报告上表现为"有效样本 14/15"），
  所以"并行"只指候选来源并行，代价是每多一路多一次 embedding 往返。
- **受控词表（`rag4prefa/terms/public_to_standard.json`）把 5 道鸿沟题全部救回，但它真
  起作用的位置不是召回，是重排。** 词表是人写的、每条带 `source`（能追到条文原话），
  匹配是对原问句做子串判断（分组 `all`，不分词）。8 条规则在口语集上命中 8 题、7 题
  未覆盖。术语只作为独立通道注入（原话那一路一条都不动），此时：

  | 配置 | `hybrid` | `rerank` | 说明 |
  |---|---|---|---|
  | 基线 | 0.333 | 0.333 | 不加词表 |
  | 词表，重排读原话 | 0.400 | 0.400 | 只多救回 1 题 |
  | 词表，重排读术语串（权重 1.0） | 0.400 | **0.667** | 5 道鸿沟题全进前 5 |

  逐题 gold 排名：`#6 挂在墙上 3 · #8 电线能换 1 · #11 老房子 1 · #14 吊顶含灯 1 ·
  #15 怎么算做好 1`；7 道词表未覆盖的题**逐项与基线一致**，3 道本来就对的题仍是第 1，
  没有任何一题被挤出去。关键不是"给对了词"这一件事，而是**召回与重排要读到同一批词**：
  gold 早就在候选池里，用口语问句重排它排 19/20/5/7/12，换成术语串排 3/1/1/1/1。
  这也解释了上一轮"扩展改善不了重排"——那是 LLM 的近义词，本来就换不动。
  复现：`python scripts/eval.py --dataset eval/dataset.paraphrase.jsonl --term-map rag4prefa/terms/public_to_standard.json --term-rerank --rewrite-weight 1.0 --modes dense,sparse,hybrid,rerank,hybrid_parallel,rerank_parallel --save`。

  **这条结论的边界必须写清楚**：8 条规则里有 5 条是看着这 15 题的失败写的，所以它证明的是
  "给对词这条链能通"（可行性），**不是**"词表能泛化"。真正的检验要等一份不参照测试结果的
  词表。真正的检验要等一份不参照测试结果的
  词表。（词表已在 2026-10-29 接进生产链路，开关 `R4P_TERM_MAP` 默认关闭，见上文
  「口语问句的术语通道」；这里记的是它作为评估开关时的第一版结论。）

  口语集扩到 50 题之后，这条的边界被量化了（`eval/paraphrase-50-20261029.md`）：

  | 组 | 题数 | rerank（原话重排） | rerank_parallel（词表 + 术语重排） |
  |---|---|---|---|
  | 词表命中 | 8 | 0.375 | **0.750** |
  | 词表未命中 | 42 | 0.762 | 0.762 |
  | 全部 | 50 | 0.700 | **0.760** |

  收益严格等于被覆盖的 8 题（救回 3 题、0 题变差），42 道未覆盖题两行的 gold 名次完全一致。
  这比 15 题那次的对照强得多（那次只有 10 道对照题）。但**新出的 35 题，词表一条都没命中**
  （命中率 0%）——8 条映射覆盖的是老 15 题的 5 个失败点，换一批不看词表出的题就是零命中。
  所以当前的结论是"机制可行、尚未证明可推广"，下一步该写一份**不看测试集**的词表再来测。
  这组数字取自等权 RRF 时期（`fusion=rrf`）。融合换成 zscore 之后同口径基线是 0.680，
  v1 用 `append` 形态重跑得到 **0.680 → 0.780**（覆盖的 8 题全部进前 5，0 题变差）；

- **词表 v2（`public_to_standard.v2.json`，28 条）是按条文建的，覆盖翻倍但增益没有增加；有收获
  的是「怎么用」，不是「做多大」。** 28 条里 23 条按语料抽出的规范用语 + 该领域日常说法写

  但**每条词条最多只覆盖 2 题**，约 0.5 题/条——它是一张按问法索引的查找表，不是知识层。

  | v1（8 条）+ append | 8 | +0.100 | 0.375 → 1.000（5 赢 0 输） | 5/8 = 62% |
  | v2（28 条）+ 纯术语串 | 15 | +0.040 | 0.667 → 0.800（5 赢 **3 输**） | 4/15 = 27% |

  三件事：

  1. **`append`（原话 + 术语串）优于 `replace`（纯术语串），是机制性的。** 纯术语串那版的
     3 道输题基线**全是第 1 名**——它们重排本来就能读懂，换查询等于拿掉信号。固定候选池、
     只换 `rerank_query` 的三方对照：原话 11/15、术语串 12/15、**原话+术语串 14/15**。
     所以 `--term-rerank append` 才是该用的形态（默认仍是 `none`，不开词表）。
  2. **泛化仍未证明，而且否定得很具体。** 两组独立切法（`public_side` 自查 / 「v1 是否也覆盖」
     这件客观事实）给出完全相同的 5 题 / 10 题分组：v2 相对 v1 **新覆盖的 10 题只多救了 1 题**，
     另外 3 次救援全落在 v1 早已覆盖的 5 题上——而那 5 题正是写词表时记得住的题。
     条数翻 3.5 倍，净增益没有增加（差值一题，在噪声地板内，不能说更低，但也不能说更高）。
  3. **单次运行的 Recall@5 有 ±1 题的地板。** 三次独立运行的基线行逐题对比：口语 48/50
     名次全同、2 题偏 1 位、0 题跨 top-5；基础 31 题上未覆盖组「涨了 1 题」纯属抖动
     （一题 = 0.032）。**小于 2 题的差别不要单独解释**，所以这一节的结论都用赢/输题数表述。

- 单进程设计（SQLite + 进程内任务）。要多副本时把 SQLite 换成 Postgres、任务换队列，接口层无需改动。
- **并发**：同一个 `sqlite3.Connection` 被请求与后台入库线程共用（`check_same_thread=False`），
  没有额外的写锁。单用户没问题，多人并发写之前应先改成每线程独立连接。
- **任务恢复**：进程重启时会把遗留的 `running/queued` 标成失败（不会永远显示"运行中"），
  但任务本身不能断点续跑，需要重新触发。
- **无身份认证**：上传与删除接口没有权限校验；「API 设置」里的用户名只是标签，不构成登录，
  别人知道用户名就能用自己的 Key 顶替。只能部署在可信内网。
- **上传无大小上限**：按后缀校验后一次性读入内存，没有流式落盘与容量限制。
- **Milvus 与中文路径**：Windows 下 Milvus Lite 无法在含非 ASCII 字符的路径下建索引（faiss 限制），
  程序会提前拒绝并自动回退 numpy；要跑 Milvus 请把数据目录指到纯 ASCII 路径。Linux 不受影响。
- **重建期间有极短不可用窗口**：全量重建（含同维度）走"写暂存集合 → rename 切换"，
  两次 rename 之间检索可能拿到集合不存在的错误。换来的是"绝不会返回新旧混杂的结果"。
- **日常一致性检查是必要条件，不是充分条件**：每个请求只比条数与模型/维度，发现不了
  "索引少了一个 id、同时多了另一个 id"这种等量替换。要确认到 id 级请跑
  `python -m rag4prefa verify`（代价是把索引主键全拉一遍，不能放进请求路径）。
  另外 SQLite 归档与向量库不在同一事务里，重建中断时会靠 `meta.index_state` 标记
  阻断检索——标记为 `ready` 之外的任何值都不提供服务，直到 `reindex` 或 `rebuild` 完成。
- **`rebuild` 的"完成"有明确判据**：归档可用（无缺行、每行带模型名、全库一套模型与维度）
  → 后端条数 = 归档条数 → 归档的模型与维度写回 `meta` 且标记回 `ready`（同一事务）。
  任一条不满足就**保留标记并返回非零**，不会出现"命令说恢复成功、实际还是查不了"。
  反过来说，归档本身残缺（有正文没向量）时 `rebuild` 帮不上忙，只能跑 `reindex` 重算。
